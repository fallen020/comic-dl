The how-to for working on comic-dl itself, in the order a contributor meets
the parts of it. Together these pages cover the whole lifecycle of a change —
from the first bug report to the release that ships it.

## The life of a change

1. **Report or pick** — an issue exists or you file one
   ([reporting](../reporting/)). The `good first issue`, `help wanted` labels
   mark ones new contributors can take.
2. **Branch** — a feature branch forks from `dev`, never from `main`.
3. **Implement** — small, signed commits, each a Conventional Commit.
4. **Gate** — run `test.sh`, `lint.sh`, and `docs.sh` locally until they pass.
5. **Review** — open a PR against `dev`; reviewers run the checklist in
   [code review](../code-review/).
6. **Merge** — squash-merged into `dev`, one commit per PR.
7. **Validate** — release-ready work is cut to `staging`, proven there, then
   released to `main` on the Monday cadence in [releasing](../releasing/).

See also the [architecture](../architecture/) guide for what each module does,
and the [site support](../../usage/site-support/) page for the supported-site
contract used by the release pipeline.
